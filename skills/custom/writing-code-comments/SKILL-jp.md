# コードコメント規律

**コメントは次の読み手への制約説明（Why not）だけ。変更経緯・修正の弁明はコミットログへ。**

字面だけ守って趣旨を破るのも違反（「これは経緯ではなく背景説明」等の言い換えを含む）。

English version: `SKILL.md` in this directory.

## 用語

| 用語 | 意味 |
|---|---|
| **Why not（制約説明）** | なぜ素直な書き方を避けたか。1行。消すと誰かが「素直な書き方」へ戻してバグらせるものだけ。 |
| **弁明** | この変更が正しい理由をレビュアーに説明すること。コードに書かない。 |
| **経緯** | 何をいつ変えたかの時系列（「XからYへ変えた際に」等）。コードに書かない。 |
| **修正宣言** | 「〜を解消する」「〜を防止する」「〜に対応する」等。コードに書かない。 |

## 判定基準

書く前に問う: **「マージ後にこのコードを読む人に必要か、それともレビュアーへの弁明か」**

- **Why not（残す・1行）**: なぜ素直な書き方を避けたか。消すと退行するものだけ。
- **弁明（書かない）**: 変更経緯、修正宣言、正当性の説明、他ファイルの改修予定
- **テストコード**: テスト名（What）が語る。同じ内容の散文コメントを重ねない

## 書き方の規則

追加するコメントと JSDoc のすべてに適用する:

- **このリポジトリの契約の言葉で書く。** 制約は、このリポジトリの用語か API の契約（仕様・型）で書く。他リポジトリの関数名・ファイル名・行番号や、判定ロジックの書き写しは、相手側が変わっても気づかれないまま古くなる。例外: 型の JSDoc に、その型が写している API スキーマのファイルを出典として書くのはよい。
- **1 つの事実は 1 か所で言う。** 1 行目・`@param`・`@returns` は、それぞれ他の行と識別子名が言っていないことだけを書く。関数の仕様（戻り値、未設定や不正値のときの値、入出力の例）は JSDoc に書いてよい。名前の言い換えは書かない。
- **平叙文 1 文で書く。** `Why not X:` のようなラベルではなく「X を使わないのは Y のため」と書く。「〜してもらう」のような依頼や、情緒を込めた副詞は入れない。
- **確定した文言は変えない。** ユーザーが確定した文言はそのまま。hook の通知やレビューの指摘は書き換える理由にならない。

## ❌/✅ 実例

コメントを直すとき **圧縮して残す** か **削除** かを選ぶ。迷ったら削除する。文言の書き直しは選択肢に入れない:

- **圧縮（パターン 1–3）**: 経緯を除いても1行の Why not が残る
- **削除（パターン 4）**: 残るのが変更説明かテスト名の繰り返しだけ

### 1. 経緯を制約説明へ圧縮

```
❌ {/*
     数字の天地中央はflexで担保する。行ボックス頼みだと外側要素の継承line-heightに
     左右され、クリック領域をbutton→aへ変えた際に中央からずれた
   */}
✅ {/* 行ボックス任せだと外側の継承line-heightに左右されるため、flexで固定する */}
```

### 2. 症状説明を落とし「なぜ使わないか」だけ残す

ライブラリのフラグや API が使えそうに見えて、特定状態では使えないとき（例: フェッチキー未確定の間 `isLoading` が false のまま）。

```
❌ // isLoadingはフェッチキーがnull（認証セッション未解決）の間もfalseのため、
   // isLoadingで判定するとハードリロード時にエラー画面が先に一瞬表示される
✅ // isLoadingはフェッチキー未確定の間もfalseになり取得中と判定できないため使わない
```

テスト — テスト名と重複する散文は削除:

```
❌ # 先週フレークしたのでリトライ追加。このテストは POST がスキップされることを確認
✅ （コメントなし — テスト名が What を語る）
```

### 3. 型に反して見えるコードの存在理由だけ残す

```
❌ // 型上は必須だが、バージョンスキュー等でこのフィールドを返さない旧レスポンスが来た場合に
   // 画面全体を TypeError で落とさず既定値へ劣化させるため、取得境界で空配列に正規化する
✅ // 型上は必須だが、legacy API がこのフィールドを返さない場合の防御
```

Go:

```
❌ // 本番インシデント #4521 後に追加。旧クライアントがフィールドを省略することがある
✅ // 旧クライアントは struct tag に反してフィールドを省略しうる — nil deref で panic しないため
```

SQL マイグレーション — 一見冗長な制約の理由:

```
❌ -- #892 ロールバック後に追加。火曜の本番で全表スキャンが無理だったので NOT VALID に
✅ -- 既存行はカラム追加前のデータを含む — バックフィル後の別マイグレーションで VALIDATE
```

### 4. 変更説明だけなら全削除

```
❌ {/*
     カード全体を直接アンカー要素にする。button > a の入れ子にすると
     フォーカスが onClick を持たない button に乗り、キーボードで遷移できず余白クリックも無反応になる
   */}
✅ 削除 — コメントなし。理由はコミットログへ。
```

テスト:

```
❌ def test_retry_excludes_non_idempotent_methods():
       # POST は重複送信でレコードが増えるのでリトライ不可 — このテストは POST がスキップされることを確認
✅ def test_retry_excludes_non_idempotent_methods():
       （コメントなし — テスト名が What を語る）
```

## 合理化テーブル

| 言い訳 | 現実 |
|---|---|
| 「レビュアーの理解を助ける」 | それは PR 本文とコミットログの仕事。マージ後のコードにはノイズ |
| 「退行の原因を記録したい」 | git blame とコミットログが恒久的に記録する |
| 「丁寧に書くほうが親切」 | マージ後の読み手に「変更前の状態」は存在しない |
| 「これは Why not だ」 | 1行に圧縮できないなら Why not ではない |
| 「経緯ではなく背景の説明だ」 | 過去形・時系列が入った時点で経緯。削除 |

## Red Flags — 検出したら削除してから完了

- 過去の状態・時系列への言及（「〜へ変えた際に」「〜だったため修正」）
- 修正宣言（「〜を解消する」「〜を防止する」「〜に対応する」）
- テスト名と同じ内容の散文
- 3行以上のブロックコメント（Why not は1行に収まる）
- 他リポジトリの関数名・ファイル名・行番号
- 他の行や識別子名を言い直しているだけの JSDoc の行
- `Why not X:` のラベルや情緒語

**ひとつでも該当したら: コメントを削除し、必要な情報はコミットメッセージへ移す。**
